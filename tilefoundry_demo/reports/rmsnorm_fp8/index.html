D001Make the RMSNorm + FP8 quantisation step match expected.pt. ACCEPTED GUIDED_TUTORIAL_REPLAY

P2-1 · 选中：reorder the arithmetic

observations
  • tilefoundry check reported output[0] equal mismatched 432 of 14336 elements and output[1] allclose max_violation 6.87445e-05
  • the failing HIR multiplied by gamma and then rounded to bf16
candidate_actions
  • loosen the comparison tolerance so the check passes
  • reorder the arithmetic so the bf16 rounding happens before the gamma multiply
expected_effect
Both predicates pass at the stated tolerance without changing the tolerance, because the failure is a rounding-order error rather than numerical noise.
observed_effect
equal mismatched 0 of 14336; allclose max_violation 0; exit status 0.
reason
The tolerance was not touched. A rounding-order error shows up as exact fp8 mismatches in a small subset of elements, which is what the report showed (432 of 14336), so the repair had to be structural.

D002Choose between the unfused and the fused placement. ACCEPTED GUIDED_TUTORIAL_REPLAY

P2-2 · 选中：fuse

observations
  • Naive ideal-ns=8697 bound-by=memory
  • Fused ideal-ns=3755 bound-by=memory
  • Naive gmem r7.23MiB/w5.47MiB@logical; Fused gmem r3.62MiB/w1.86MiB@logical
candidate_actions
  • optimise the arithmetic, since the step is a reduction plus a quantisation
  • fuse the two functions so the normalized rows never reach gmem
expected_effect
gmem traffic drops by the round trip of the normalized rows, and the modelled time drops with it.
observed_effect
gmem read and write each dropped 3784704 B (264x7168x2), and ideal-ns fell from 8697 to 3755.

Both placements report bound-by=memory, so arithmetic is not the lever. The traffic that disappeared is exactly the intermediate rows, which is the mechanism fusion was chosen for.

D003Decide whether a runtime twin is needed before measuring. ACCEPTED GUIDED_TUTORIAL_REPLAY

P2-3 · 选中：build and check the twin, then time it

observations
  • the HIR reports are a static cost model, not a measurement
  • the tutorial ships a hand-written Triton kernel that claims a speedup
candidate_actions
  • compare the static ideal-ns figures directly against the torch baseline
  • build a Triton twin, check it against the same expected.pt, then time it
expected_effect
The twin gives a measured counterpart to the static prediction, and checking it first keeps a broken kernel from producing a meaningless time.
observed_effect
The twin passed both predicates on the H200 under Triton 3.5.1, so the timed kernel was correct.
reason
ideal-ns counts bytes divided by bandwidth. It is not a duration, so it cannot be compared to a measured millisecond figure without inventing a conversion.

D004Decide how to report the measured speedup. ACCEPTED GUIDED_TUTORIAL_REPLAY

P2-4 · 选中：interleave the arms and report a range

observations
  • the torch baseline per-round median moved between 0.1078 ms and 0.210 ms across runs
  • that movement exceeds the 4.2x gap being described
  • timing one arm to completion before the other lets clock variation load onto one arm
candidate_actions
  • report a single ratio from one pair of runs
  • interleave the arms per round and report the median of per-round medians with a range
expected_effect
The reported ratio no longer depends on which arm ran while the device was warmer, and the spread shows how stable it is.
observed_effect
5 alternating rounds gave a torch median of 0.1078 ms against a twin median of 0.02566 ms, a speedup of 4.09x to 4.23x with a median of 4.18x. An earlier run measured 4.44x to 4.58x, a median of 4.52x, so the range across sessions is wider than the range within one session.
reason
A single ratio would have claimed more precision than the measurements support. The range is the honest summary and the session-to-session spread is stated separately.

D005Find a placement that beats the fused placement. REJECTED AGENT_EXPERIMENT

P2-5 · 选中：keep the fused sharding, move the activations from rmem to smem

observations
  • both tutorial placements are bound by memory
  • the fused placement already removed the intermediate gmem round trip
  • the fused placement still holds the activations in rmem for the whole func: rmem r70.57MiB/w56.07MiB@logical
candidate_actions
  • shard the CTA axis first in a 4-D layout
  • keep the fused sharding but stage the activations through smem instead of rmem
expected_effect
On-chip residency moves to a different memory level while gmem traffic and arithmetic stay the same. If on-chip residency were the limit, the modelled time would fall; if gmem were the limit, it would not move.
observed_effect
ideal-ns stayed at 3755 with bound-by=memory. rmem fell to r16B/w0 and smem took the activations at r70.57MiB/w56.07MiB@logical.
reason
The placement is correct, but it does not lower the modelled time. The hypothesis was that on-chip residency was a limit; the report shows it is not, because gmem is the bound. Recording this as an optimisation would be false.
